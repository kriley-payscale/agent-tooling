# Filtering the plan cache by SQL text

In T-SQL `LIKE`, `[` opens a character-class wildcard. EF-generated SQL is entirely bracketed identifiers, so a predicate pasted from the emitted statement matches nothing and returns zero rows with no error. That looks identical to "the statement is not in the cache." Match an unbracketed fragment: a projection alias, a literal, or a table name without delimiters. When only a bracketed fragment is distinctive, escape it (`LIKE '%[[]c2[]]%'`). Treat a zero-row `LIKE` against `sys.dm_exec_sql_text` as an unproven filter until the same query returns rows for a deliberately broad pattern.

`sys.dm_exec_sql_text(qs.sql_handle)` returns the **whole batch**, while `query_stats` rows are per statement. A `WHERE t.text LIKE '%fragment%'` filter therefore selects every statement of every batch containing the fragment, and any `SUM` or `ORDER BY` over that result silently mixes in sibling statements — including unrelated background work sharing the batch. Filter on the statement extracted with `SUBSTRING(t.text, qs.statement_start_offset/2, …)` inside a CTE, not on `t.text`. An implausibly large `execution_count` is the tell.

When bracketing one request with two `query_stats` dumps and diffing them, a plan evicted and recompiled between the snapshots reports **reset** counters, so the naive subtraction goes negative and the statement drops out of the diff — which reads as "this query no longer runs" rather than "its plan was evicted." Treat `post.execution_count < pre.execution_count` as an eviction and use the post row as the delta. `execution_count` increments when a statement starts while `total_elapsed_time` updates at completion, so a snapshot can catch a half-updated row.

When comparing two translation forms of the same statement before and after a query-shape change, discriminate on the fragment that actually changed, not on a general keyword associated with the old form. The same keyword often survives elsewhere in the statement for an unrelated parameter that was deliberately left alone, so the new plan classifies as the old one and the result reads as "the change did not take effect" for a query that in fact changed correctly. Key the `CASE` on a distinctive substring of the new form — a literal value, a rewritten operator — and confirm the two arms return matched `execution_count` before trusting the comparison.

Keep the `LIKE` predicate on the full extracted statement text. Do not review or grep a `LEFT(statement_text, N)` preview for the distinctive fragment. Projection aliases and correlated `CASE` labels often sit thousands of characters into the `SELECT` list, so a truncated dump looks like a zero-row miss even when the statement is in cache. If the output must be narrow, emit a `CHARINDEX` window around the fragment the `WHERE` already matched.

A plan-cache snapshot whose `WHERE` clause contains the same text fragment it is searching for will match itself. The dump then appears in a pre/post delta as a `NEW` statement with real elapsed time. Discriminate snapshot batches (`dm_exec_query_stats` / `sys.dm_exec_sql_text`) out of the delta, or bind the search fragment as a parameter so it does not appear as a literal in the batch text.

Table name plus `avg_rows` does not identify the statement currently running after a projection was narrowed. The previous wide form often stays in cache with the same row count and a much higher `avg_ms`. Discriminate on an alias this revision added or removed (`NOT LIKE` a dropped column alias, or `LIKE` a remaining one the old form lacked). Confirm `avg_cpu_ms` against the in-process probe before treating the cache row as the request under test.
